# 01 Completion Gate 与验证证据失效

## 一、背景：为什么需要 Completion Gate

ReAct 循环的终止条件，是 Agent 框架最容易"被模型骗"的地方。

PAICLI 当前的 `Agent.java` 用一个 `while(true)` 循环驱动 ReAct：每一轮把历史消息发给 LLM，如果 LLM 这一轮没有再调用工具，循环就结束，把最后一条 assistant 消息当作最终答案返回。这个判断本身没有错，它符合 ReAct 的原始定义——"模型不再需要行动，就认为它已经想清楚了"。

问题在于，"不再调用工具"和"任务真的完成"之间，并不是等号。模型完全可能在没真正验证结果的情况下，直接给出一句话总结，然后停手。比如让它"把 `UserService.java` 里的 `getUserById` 方法改成返回 `Optional<User>`"，模型可能调了一次 `write_file`，然后下一轮直接说"已完成修改"，循环就结束了。至于文件是不是真的改对了、有没有引入编译错误、有没有漏掉调用方，循环本身一无所知。

这不是 PAICLI 独有的问题，几乎所有 ReAct 风格的 Agent 都会遇到。但 MyCodeAgent 在这件事上做了一个值得借鉴的设计：它不依赖"模型自己说完成"，而是用一套确定性的 Completion Gate 去推断"任务到底需要什么证据才算完成"，并且在这些证据被污染时主动失效。

本篇要讨论的，就是把这套 Completion Gate 的思路迁移到 PAICLI 的可行性。

## 二、PAICLI 现状：循环停在"模型不动作"那一刻

要理解借鉴的价值，先得看清楚 PAICLI 现在到底是怎么停的。

在 `Agent.java` 的主循环里，每一轮的流程大致是：组装 system prompt 和 conversationHistory → 调用 `LlmClient.chat` → 解析返回的 toolCalls → 如果有 toolCalls 就走 `ToolRegistry.executeTools` 并把结果回灌到 history → 如果没有 toolCalls，就把 assistant 消息写进 history、走收尾逻辑、跳出循环。也就是说，"是否继续"完全由 LLM 这一轮有没有给出 tool call 来决定。

这套逻辑的优点是简单、可控、和 OpenAI function calling 的语义天然对齐。缺点是它把"完成判定"这件事完全外包给了模型，框架层面没有任何确定性的兜底。模型说完成就完成，模型说继续就继续，框架只是个忠实的搬运工。

这带来两个具体的风险。第一个风险是"虚假完成"：模型可能在证据不足时就停手，比如只读了文件没改、或者改了但没验证，就给出"已完成"。第二个风险是"过度行动"：模型可能在已经达成目标后还在反复调用工具，浪费 token 和时间，直到它自己觉得够了才停。PAICLI 现在没有任何机制去识别这两种情况，只能靠 system prompt 里写一些"完成后请确认"之类的软提示，模型听不听全凭自觉。

另外，PAICLI 的 `revert_turn` 工具虽然能撤销上一轮，但它是给模型自己用的纠错手段，不是框架层面的完成校验。模型如果根本没意识到自己错了，就不会主动调用 `revert_turn`。这进一步说明，完成判定不能只靠模型的自我意识，需要框架介入。

## 三、MyCodeAgent 的解法：DeterministicCompletionVerifier 与证据失效

MyCodeAgent 在这件事上的设计，核心是三个动作：推断完成要求、收集验证证据、在证据被污染时主动失效。这三步由一个叫 `DeterministicCompletionVerifier` 的组件串起来。

第一步是推断完成要求。它不是让模型自己判断"我完成了吗"，而是在任务开始时（或第一次拿到 user 消息时），用一次额外的 LLM 调用或规则推断，把"这个任务要算完成，需要满足哪些可观测的条件"提取出来。比如"修改某个方法"这个任务，推断出的完成要求可能包含：目标文件被写入过、目标方法签名符合预期、没有引入新的编译错误。这些条件是确定性的、可观测的，不是模型的主观判断。

第二步是收集验证证据。在 ReAct 循环推进的过程中，框架会把每一次工具调用的结果拿来和完成要求做匹配。比如 `write_file` 成功了，就记一条"目标文件已被写入"的证据；`read_file` 读到了修改后的内容且签名符合，就记一条"签名符合"的证据。这些证据不是模型自己声称的，而是工具执行结果里客观存在的。

第三步，也是最关键的一步，是证据失效。MyCodeAgent 规定：一旦在验证证据收集完成之后，又发生了任何"变更型"工具调用（比如 `Edit`、`Write`），之前收集到的所有验证证据全部作废，必须重新收集。这个设计的直觉非常朴素——你刚验证完文件是对的，紧接着又改了文件，那之前的验证自然就不算数了。它直接堵死了"模型先读一遍确认没问题，再偷偷改一下，然后说完成"这种骗法，因为"再偷偷改一下"这个动作本身就把之前"确认没问题"的证据清空了。

这三步合在一起，就把"完成判定"从模型的主观陈述，变成了框架的客观校验。模型说完成只是必要条件，框架确认证据齐全才是充分条件。

## 四、迁移到 PAICLI 的设计建议

把这套思路搬进 PAICLI，不需要推翻现有的 ReAct 循环，而是在循环的收尾处加一道"完成闸门"。下面分几层说清楚怎么改。

### 4.1 新增的类与职责

建议在 `com.bettercli.agent` 包下新增三个核心类型，保持和现有 `Agent` / `PlanExecuteAgent` / `SubAgent` 同一层级。

第一个是 `CompletionRequirement`，一个不可变的值对象，描述一条完成要求。它至少要包含：要求类型（文件写入、签名匹配、编译通过、测试通过等）、目标对象（哪个文件、哪个符号）、以及一个可选的校验器描述。一个任务对应一个 `List<CompletionRequirement>`，推断出来后就固定下来。

第二个是 `CompletionVerifier`，负责两件事：一是根据 user 的原始任务推断出 `List<CompletionRequirement>`，二是在循环推进时把工具执行结果转成证据，并判断证据是否覆盖了所有要求。它对外暴露两个方法：`inferRequirements(userMessage)` 返回要求列表，`verify(toolCallHistory)` 返回一个 `VerificationResult`，里面包含已满足的要求、未满足的要求、以及是否被污染的标记。

第三个是 `EvidenceInvalidator`，负责证据失效逻辑。它监听工具调用，一旦发现"变更型"工具（PAICLI 里就是 `write_file`，以及 MCP 里任何被标记为 mutating 的工具）在证据收集完成之后被调用，就把当前的证据集标记为失效，强制 `CompletionVerifier` 重新收集。

### 4.2 与现有 ReAct 循环的衔接

衔接点在 `Agent.java` 主循环里"LLM 没有给出 tool call"的那个分支。现在这个分支直接收尾，改成先过一道闸门：调用 `CompletionVerifier.verify`，如果返回"证据齐全且未污染"，才真正收尾；如果返回"证据不足"，不直接结束循环，而是往 conversationHistory 里注入一条系统提示，告诉模型"以下完成要求尚未满足：……，请继续行动或说明无法满足的原因"，然后让循环继续。如果模型在下一轮依然不调用工具且仍无法满足，再允许它以"无法完成"收尾，避免死循环。

这里有一个关键细节：注入的提示必须是系统级的、带证据的，而不是泛泛的"请再检查一下"。MyCodeAgent 的经验是，模糊的提示会让模型陷入"我明明做完了你为什么让我继续"的拉锯，而把"缺哪条证据"明确列出来，模型通常能立刻补上。

### 4.3 变更型工具的识别

PAICLI 的内置工具里，`write_file` 是明确的变更型工具。但 MCP 动态工具是按 server 加载的，框架事先不知道哪个 MCP 工具会改东西。建议在 `Tool` 类型上加一个 `mutating` 布尔字段，内置工具直接标注，MCP 工具默认按 mutating 处理（保守策略），用户可以在 `mcp.json` 里用 `mutating: false` 显式声明某个 MCP 工具是只读的。这样 `EvidenceInvalidator` 就能统一判断。

这个 `mutating` 标记顺带还能解决另一个问题：并行工具执行时的安全性。PAICLI 现在所有工具都一股脑并行，没有区分只读和变更。有了 `mutating` 标记后，可以把变更型工具强制串行执行，只读工具继续并行，降低竞态风险。这一点在第五篇会单独展开。

### 4.4 完成要求的推断方式

`CompletionVerifier.inferRequirements` 怎么实现，是这套设计里成本最高的一环。有两种路线。

第一种是规则推断，完全不依赖 LLM。它基于 user 消息里的关键词做模式匹配，比如出现"修改/重构/重命名 + 文件名"，就生成"目标文件被写入"和"符号匹配"两条要求。优点是零额外 token、完全确定性；缺点是覆盖不了自然语言的多样性，复杂任务推断不出来。适合作为兜底。

第二种是 LLM 推断，在任务开始时多调一次 LLM，让它输出结构化的完成要求列表。优点是覆盖面广、能处理复杂任务；缺点是多花一次 LLM 调用的成本和延迟，而且 LLM 自己也可能推断错。建议采用"LLM 推断为主、规则兜底"的混合策略：先尝试 LLM 推断，如果失败或返回为空，退回规则推断。推断结果要缓存，同一个任务不重复推断。

为了控制成本，可以加一个开关：只有当任务看起来是"变更型"任务时才启用 LLM 推断，纯问答任务（比如"解释这段代码"）直接跳过 Completion Gate，因为没有变更型工具调用，证据失效逻辑也不会触发，强行推断反而浪费。

### 4.5 与 Plan-and-Execute 路径的关系

PAICLI 有三条主路径，Completion Gate 主要服务 ReAct 路径。Plan-and-Execute 路径里，`PlanExecuteAgent` 已经有 `ExecutionPlan` 和 `Task` 的概念，每个 Task 有自己的完成判定，天然适合把 `CompletionRequirement` 挂到每个 Task 上。建议在 `Task` 类型上加一个 `List<CompletionRequirement>` 字段，`Planner` 生成计划时一并生成完成要求，`PlanExecuteAgent` 执行每个 Task 时复用 `CompletionVerifier`。这样三条路径共享同一套完成判定逻辑，避免重复实现。

Multi-Agent 路径（`AgentOrchestrator`）的完成判定更复杂，因为子任务之间有依赖。本篇不展开，留到后续单独评估。

## 五、迭代步骤

把这套设计落地到 PAICLI，建议分成五步走，每一步都能独立验证、独立合并，降低风险。

第一步，先做"变更型工具标记"这一件最小的事。在 `Tool` 类型上加 `mutating` 字段，给内置工具标注，MCP 工具默认 mutating。这一步不涉及任何循环逻辑改动，纯数据建模，可以单独提一个 PR，配合单元测试验证标注正确。

第二步，实现 `EvidenceInvalidator` 的骨架，但先不接进循环。让它能监听工具调用历史、识别变更型工具、维护证据集和失效标记。这一步可以写充分的单元测试，覆盖"先验证后变更→失效""只读工具不失效""多次变更连续失效"等场景。

第三步，实现 `CompletionVerifier` 的规则推断版本，不接 LLM。先把规则推断和证据收集跑通，验证"框架能识别证据是否齐全"这件事在 PAICLI 的工具语义下成立。这一步的产出是一个能独立运行的 `CompletionVerifier`，输入是工具调用历史，输出是 `VerificationResult`。

第四步，把 Completion Gate 接进 `Agent.java` 的 ReAct 循环，但默认关闭，用配置项 `bettercli.completion_gate.enabled` 控制。开启后，在收尾分支插入校验逻辑，证据不足时注入提示让循环继续。这一步要重点测试"不死循环"——模型如果反复无法满足，要有最大重试次数兜底。

第五步，加入 LLM 推断和 Plan-and-Execute 路径的集成。这一步是功能完整化，前面四步已经把骨架搭好，这步主要是补全推断能力和多路径复用。

每一步都对应一个文档更新点：第一步改 `AGENTS.md` 的工具集说明，第二到四步在 `docs/` 下新建一篇 `phase-24-completion-gate.md` 记录设计，第五步更新 `docs/agents-reference.md`。

## 六、测试方案

Completion Gate 的测试要分三层，因为它的正确性既依赖单个组件的逻辑，也依赖组件之间衔接的时序。

第一层是组件单元测试。`CompletionRequirement` 的不可变性和相等性；`EvidenceInvalidator` 在各种工具调用序列下的失效行为；`CompletionVerifier` 的规则推断覆盖率和证据匹配准确性。这些用纯 Java 单元测试覆盖，不依赖 LLM。

第二层是循环集成测试。用 mock 的 `LlmClient` 构造固定的工具调用序列，验证 `Agent.java` 在 Completion Gate 开启时的行为：证据齐全时正常收尾、证据不足时注入提示继续、变更后证据失效时强制重新验证、达到最大重试时以"无法完成"收尾。这一层最关键的是覆盖"模型试图骗过 Gate"的场景，比如先读后改再说完成、或者反复声称完成但证据始终不足。

第三层是端到端手测。挑几个典型的变更型任务（改方法签名、修 bug、加日志），在真实 LLM 下跑 ReAct，观察 Completion Gate 是否真的拦住了虚假完成、注入的提示是否让模型有效补全。这一层不求全覆盖，挑三五个代表性场景即可。

测试里有一个容易忽略的点：证据集本身要是可序列化的，因为 `VerificationResult` 可能要写进 `AuditLog` 供事后审计。建议证据用简单的 JSON 结构表示，避免引用不可序列化的工具对象。

## 七、风险与权衡

这套设计不是没有代价，落地前要想清楚几个权衡。

第一个权衡是延迟和成本。Completion Gate 在变更型任务上至少多一次 LLM 推断调用，在证据不足时还会让循环多走几轮。对于 PAICLI 这种面向商业使用、强调响应速度的产品，这部分开销要可控。缓解办法是前面说的开关和"仅变更型任务启用"的过滤，把开销限制在真正需要的场景。另外 LLM 推断可以复用主模型的廉价档位，不必用最强模型。

第二个权衡是"无法完成"的边界。Completion Gate 把"模型说完成但证据不足"从直接收尾改成了"继续行动"，但如果任务本身就没有可观测的完成条件（比如"帮我构思一个方案"这种开放性任务），Gate 会一直认为证据不足，把模型逼进死循环。缓解办法是：推断阶段如果识别不出任何可观测要求，就生成一个"用户确认满意"的软要求，让模型可以通过"询问用户"来满足；同时保留最大重试次数兜底，达到上限后允许以"无法完全验证，请用户确认"收尾，而不是无限循环。

第三个权衡是推断准确性。LLM 推断出的完成要求本身可能不合理，比如要求"测试全部通过"，但项目本来就没有测试，Gate 就会一直卡住。缓解办法是推断结果要带一个"可跳过"标记，模型可以在行动中说明"该要求不适用"，`CompletionVerifier` 接受这种说明后把该要求标记为已满足（或移除）。这本质上是给 Gate 留一个人工/模型介入的逃生口。

第四个权衡是和现有 `revert_turn` 的关系。`revert_turn` 本身是变更型操作（它撤销上一轮），但它撤销的恰恰可能是污染证据的那次变更。建议把 `revert_turn` 特殊处理：它执行后，证据集回滚到被撤销那一轮之前的状态，而不是简单失效。这需要 `EvidenceInvalidator` 维护证据的版本历史，复杂度上升一档，但语义上更正确。

第五个权衡是 MCP 工具的 mutating 默认值。默认 mutating 会让大量只读 MCP 工具（比如 `web_search`、`take_snapshot`）被误判为变更型，导致证据频繁失效。缓解办法是给常用 MCP server 预置 mutating 白名单（类似 PAICLI 现在给 `step_search` 预置那样），减少用户手动配置的负担。

## 八、小结

Completion Gate 要解决的核心问题，是 ReAct 循环把"完成判定"完全外包给模型带来的虚假完成风险。MyCodeAgent 的解法是把判定权收回到框架，用确定性的证据收集和证据失效机制，让"模型说完成"变成"框架确认完成"的必要非充分条件。

迁移到 PAICLI 的关键不在于照搬 `DeterministicCompletionVerifier` 的代码，而在于接受一个设计原则：Agent 框架不应该无条件相信模型的自我陈述，尤其是涉及变更和完成这种高代价的判断点。PAICLI 现有的 `revert_turn`、`AuditLog`、HITL 审批其实都已经在践行"不完全相信模型"的原则，Completion Gate 只是把这个原则补到了循环终止这个最容易被忽略的环节。

落地时最大的风险不是技术实现，而是"无法完成"边界的拿捏——Gate 太严会让开放性任务死循环，太松又退回原状。建议先以最小代价（规则推断 + 变更型标记 + 默认关闭）把骨架立起来，用真实任务跑一段时间，观察 Gate 拦截虚假完成的频率和误伤正常完成的概率，再决定是否启用 LLM 推断和默认开启。这种灰度推进，比一次性把完整方案上线更稳妥。

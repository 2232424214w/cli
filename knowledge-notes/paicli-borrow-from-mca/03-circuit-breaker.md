# 03 工具熔断机制（Circuit Breaker）

## 一、背景：失败工具的"拖累"效应

Agent 框架里一个容易被低估的问题，是某个工具反复失败时对整个会话的拖累。

PAICLI 的 ReAct 循环里，工具调用是模型推进任务的主要手段。当某个工具因为环境问题反复失败时——比如 `grep_code` 因为 `ripgrep` 没装好一直报错、某个 MCP server 掉线导致 `mcp__xxx` 一直超时、`web_fetch` 因为网络问题持续返回 502——模型会陷入一种很浪费的循环：它看到工具失败，倾向于换个参数再试，再失败再换，或者反复重试同一个调用，消耗大量 token 和时间，却推进不了任务。

更糟的是，模型对"工具持续失败"和"工具偶尔失败"缺乏区分能力。偶尔失败的工具（比如一次网络抖动）值得重试，持续失败的工具（比如 server 挂了）重试毫无意义，反而应该让模型知道"这个工具现在不可用，请换思路"。但 PAICLI 现在给模型的反馈只有每次调用的成功或失败结果，没有任何"这个工具整体健康度如何"的信号，模型只能基于单次结果盲目决策。

PAICLI 现在对工具失败的处理，是在 `executeTools` 里捕获异常、把异常信息包装成工具结果返回给模型，仅此而已。没有失败计数、没有降级、没有熔断。一个坏掉的工具会一直被调用、一直失败、一直消耗资源，直到模型自己"学乖"不再调用它——但模型往往学不乖，因为每次失败它都看到不同的错误信息，以为是参数问题。

MyCodeAgent 在这件事上引入了经典的 Circuit Breaker 模式，值得 PAICLI 借鉴。

## 二、PAICLI 现状：无差别重试，无健康度感知

看清楚 PAICLI 现在怎么处理工具失败。

在 `ToolRegistry.executeTools` 的执行体里，每个工具调用被包在一个 try-catch 里，异常会被捕获并转成 `ToolExecutionResult`，状态标记为失败，错误信息塞进结果。这个结果会被回灌到 conversationHistory，作为 `tool` 角色的消息发给模型。模型在下一轮看到这个失败结果，自己决定下一步怎么办。

这套逻辑的问题在于，框架层面对"失败"是没有任何记忆的。每一次工具调用都是独立事件，框架不记录"这个工具今天已经连续失败 8 次了"，也不记录"这个 MCP server 已经 5 分钟没响应过了"。模型每次看到失败，都像第一次看到，没有历史上下文帮它判断"这是偶发还是系统性故障"。

具体到几个场景。第一个是 MCP server 掉线：PAICLI 的 `McpServerManager` 有 server 状态管理（`McpServerStatus`），但这个状态只反映 server 进程是否启动，不反映工具调用是否成功。server 显示 RUNNING 但工具一直超时的情况完全可能发生，模型却拿不到"这个 server 的工具在持续失败"的信号。第二个是 `execute_command` 命令不存在：如果用户环境里没有某个命令，模型可能反复尝试不同参数，每次都失败，框架不会主动提示"这个命令在你环境里不可用"。第三个是网络类工具（`web_search`、`web_fetch`）在网络抖动时：偶尔失败重试有意义，但 PAICLI 没有自动重试，全靠模型手动重试，模型又倾向于换参数而非原样重试，往往越换越错。

本质上，PAICLI 缺少一个"工具健康度"的概念，把所有工具调用都当作无状态的独立事件处理，没有把失败历史聚合成可决策的信号。

## 三、MyCodeAgent 的解法：CircuitBreaker 三态机

MyCodeAgent 给每个工具配了一个 `CircuitBreaker`，用经典的三态机管理工具健康度：CLOSED（正常）、OPEN（熔断，拒绝调用）、HALF_OPEN（半开，试探性放行一次）。

正常状态下（CLOSED），工具调用照常执行，框架同时记录每次调用的成功或失败。当连续失败次数达到阈值（比如 5 次），或者短时间内失败率超过比例（比如 10 次里失败 8 次），熔断器跳闸，进入 OPEN 状态。进入 OPEN 后，对该工具的后续调用不再真正执行，而是直接快速返回一个"该工具当前不可用（已熔断）"的错误，不消耗实际资源。这个快速失败本身就是给模型的信号——你不用再试了，这个工具坏了。

OPEN 状态会持续一段冷却时间（比如 60 秒），冷却过后进入 HALF_OPEN。HALF_OPEN 状态下，框架放行一次调用试探：如果这次成功，说明工具恢复了，熔断器回到 CLOSED 恢复正常；如果这次还是失败，说明工具还没好，重新回到 OPEN 再等一轮冷却。这个机制让工具"自我修复"——不需要人工干预，工具恢复后自动重新可用。

这套三态机的价值在于两点。第一，它把"工具持续失败"从模型的负担变成了框架的责任，框架主动拦截无意义的重试，节省 token 和时间。第二，它给模型一个明确的、和单次失败不同的信号——"已熔断"意味着系统性故障，模型应该换思路而不是重试，这比让模型从一堆相似错误信息里自己猜要有效得多。

## 四、迁移到 PAICLI 的设计建议

### 4.1 新增的类与职责

建议在 `com.bettercli.tool` 包下新增 `ToolCircuitBreaker` 和 `ToolHealthRegistry` 两个类型。

`ToolCircuitBreaker` 是单个工具的熔断器，封装三态机和计数逻辑。它对外暴露三个方法：`beforeCall()` 在调用前检查状态，返回是否允许调用（CLOSED/HALF_OPEN 允许，OPEN 拒绝并附带剩余冷却时间）；`recordSuccess()` 和 `recordFailure(error)` 在调用后记录结果，更新状态机。状态用枚举 `BreakerState` 表示，阈值和冷却时间作为构造参数，可配置。

`ToolHealthRegistry` 是所有工具熔断器的注册中心，按工具名索引。它在 `ToolRegistry` 初始化时为每个内置工具和动态加载的 MCP 工具创建一个 `ToolCircuitBreaker`。它对外暴露 `getBreaker(toolName)` 供 `executeTools` 查询，以及 `snapshot()` 返回所有工具的健康度摘要，供 system prompt 注入或 `/tool-health` 命令展示。

### 4.2 与 executeTools 的衔接

衔接点在 `executeToolsUnrestricted` 的执行体里。现在每个工具调用直接执行，改成在执行前先调用 `breaker.beforeCall()`，如果被拒绝，不执行实际工具，直接构造一个 `ToolExecutionResult` 标记为"工具已熔断"，附带熔断原因和预计恢复时间。如果允许调用，执行后根据成功或失败调用 `recordSuccess` / `recordFailure`。

这里有个细节：熔断的快速失败结果要和正常失败区分开，让模型能识别。建议在结果里加一个 `circuitOpen: true` 的标记，错误信息明确写"该工具因连续失败已被熔断，预计 N 秒后恢复，请改用其他方式"。模型看到这个信号，通常会主动换工具或换思路，而不是傻等或重试。

### 4.3 失败的分类

不是所有失败都该触发熔断。MyCodeAgent 的经验是，要把失败分成"可熔断"和"不可熔断"两类。可熔断的是环境性、持续性的失败：MCP server 掉线、命令不存在、网络持续不可达、工具内部异常。不可熔断的是参数性、一次性的失败：路径不存在、参数格式错、权限拒绝——这些是模型换参数就能解决的，熔断它们反而妨碍模型自我修正。

PAICLI 实现时，建议给 `ToolExecutionResult` 加一个 `failureCategory` 字段，由工具 executor 或 `ToolRegistry` 的异常处理逻辑分类。`PolicyException`（PathGuard/CommandGuard 拒绝）归为不可熔断（参数问题）；`IOException` 且是网络/连接类的归为可熔断；工具内部抛出的运行时异常归为可熔断（保守）。只有可熔断的失败才喂给 `recordFailure`，不可熔断的不计入熔断计数，避免模型因为参数错误把一个本来正常的工具熔断了。

### 4.4 健康度信号注入

熔断器的价值一半在拦截，一半在信号。建议把 `ToolHealthRegistry.snapshot()` 的摘要注入 system prompt，让模型在规划阶段就知道哪些工具当前不可用。摘要格式要简洁，只列非健康工具，比如"当前不可用工具：`web_fetch`（熔断中，预计 45 秒后恢复）、`mcp__github__create_pr`（server 连接失败）"。健康工具不列，避免噪音。

这个注入和 PAICLI 现有的 MCP server 状态注入是同一类机制，可以复用 `PromptAssembler` 的注入点。配合一个 `/tool-health` 斜杠命令，让用户也能随时查看工具健康度，便于调试环境问题。

### 4.5 MCP 工具的特殊处理

MCP 工具的熔断要和 `McpServerManager` 的 server 状态联动。当一个 MCP server 的工具反复失败，往往不是单个工具的问题，而是整个 server 的问题（进程挂了、网络断了）。建议在 `ToolCircuitBreaker` 触发 OPEN 时，通知 `McpServerManager` 检查对应 server 状态，如果 server 已经不可达，直接把整个 server 的所有工具一起熔断，而不是逐个工具各自熔断——这样模型看到的是"这个 server 不可用"而不是"这个 server 的工具一个个坏掉"，信号更清晰。

反过来，`McpServerManager` 检测到 server 恢复时，主动重置该 server 所有工具的熔断器到 HALF_OPEN，让工具随 server 恢复一起恢复。这种联动让熔断器和 server 管理形成闭环，而不是两套独立的状态机打架。

## 五、迭代步骤

第一步，实现 `ToolCircuitBreaker` 的三态机逻辑，纯单元测试，不接 `executeTools`。覆盖状态转换、计数、冷却、HALF_OPEN 试探等所有路径。

第二步，实现 `ToolHealthRegistry` 和失败分类逻辑，给 `ToolExecutionResult` 加 `failureCategory` 字段，让现有工具的失败先被分类，但不触发熔断（只记录）。这一步把分类基础设施立起来，便于观察各类失败的实际分布。

第三步，把熔断器接进 `executeTools`，但阈值设得很高（比如连续 20 次失败才熔断），默认开启。高阈值保证正常使用几乎不会触发，但极端场景能兜住。观察真实环境下的熔断触发频率。

第四步，加入 system prompt 健康度注入和 `/tool-health` 命令，让信号对模型和用户都可见。

第五步，加入 MCP server 联动，把熔断器和 `McpServerManager` 打通。

文档同步：第一步起在 `docs/` 新建 `phase-26-circuit-breaker.md`，第三步更新 `AGENTS.md` 工具行为说明，第四步更新提示词注入相关文档。

## 六、测试方案

第一层，`ToolCircuitBreaker` 单元测试。覆盖：CLOSED 下连续失败到阈值跳 OPEN、OPEN 期间 `beforeCall` 拒绝并返回剩余冷却、冷却结束转 HALF_OPEN、HALF_OPEN 成功转 CLOSED、HALF_OPEN 失败转 OPEN、成功计数重置失败计数（或按滑动窗口计算失败率）、并发调用的计数安全。

第二层，`executeTools` 集成测试。构造一个 mock 工具持续抛异常，验证：前几次正常执行并失败、达到阈值后调用被快速拒绝、拒绝结果带 `circuitOpen` 标记、冷却后试探恢复。再构造一个偶发失败的工具（失败-成功-失败-成功），验证不会被误熔断。

第三层，失败分类测试。验证 `PolicyException` 不触发熔断计数、网络 `IOException` 触发、参数错误不触发。这层确保熔断只对"该熔断的"失败生效。

第四层，MCP 联动测试。mock 一个 MCP server 的多个工具同时失败，验证整 server 熔断而非逐工具熔断；mock server 恢复，验证工具熔断器一起重置。

第五层，端到端手测。故意配置一个不存在的 MCP server 或断网环境，跑真实任务，观察熔断是否触发、模型是否根据"已熔断"信号换思路、任务是否还能推进。

## 七、风险与权衡

第一个权衡是熔断阈值和冷却时间的调参。阈值太低，偶发失败就熔断，正常工具被误伤；阈值太高，熔断形同虚设。冷却太短，工具没恢复就试探，浪费；冷却太长，工具早好了却迟迟不放行。建议阈值和冷却都做成可配置，默认值偏保守（高阈值、中等冷却），再根据真实数据调整。不同工具可以配不同参数——网络类工具冷却短（网络抖动恢复快）、MCP 类工具冷却长（server 重启慢）。

第二个权衡是熔断可能掩盖真实问题。一个工具反复失败，可能是环境真的有问题（比如 `ripgrep` 没装），熔断只是让模型不调用它，但根本问题没解决。缓解办法是熔断时同时记录到 `AuditLog` 并在 `/tool-health` 里醒目展示，引导用户去修环境，而不是让熔断器默默兜着。熔断是应急手段，不是长期方案。

第三个权衡是和并行执行的交互。一轮里模型可能并行调用同一个工具多次（比如同时 grep 三个不同模式），如果这个工具刚好在熔断边缘，并行调用可能同时触发多个失败计数。建议熔断计数按"调用"而非"批次"计，并行调用各自独立计数，避免一次并行把熔断器提前打爆。但 `beforeCall` 的拒绝要保证一致性——一旦某个调用把状态推到 OPEN，同批次后续调用应被拒绝，这需要 `beforeCall` 加锁或用原子状态。

第四个权衡是熔断信号的语义清晰度。"已熔断"这个信号要让模型准确理解。如果错误信息写得太技术（"CircuitBreaker is OPEN"），模型可能不知所云。建议错误信息用自然语言写清楚"该工具因多次失败暂时禁用，请改用其他工具或稍后重试"，并配合 system prompt 里的健康度摘要，双管齐下让模型拿到正确信号。

第五个权衡是是否对内置工具都启用熔断。像 `read_file`、`grep_code` 这种核心工具，熔断它们可能让模型直接没法干活。建议核心只读工具默认不熔断（或阈值极高），只对 MCP 工具、`execute_command`、网络类工具默认启用熔断。这避免熔断器好心办坏事，把模型赖以生存的工具给禁了。

## 八、小结

工具熔断要解决的，是 PAICLI 在工具失败处理上"无记忆、无降级"的短板。当前每次工具失败都是孤立事件，框架不聚合失败历史、不主动拦截无意义重试、不给模型系统性故障的信号，导致模型在坏掉的工具上反复浪费资源。

MyCodeAgent 的 Circuit Breaker 三态机给了一个成熟参照：用 CLOSED/OPEN/HALF_OPEN 管理工具健康度，连续失败就熔断快速拒绝，冷却后试探性恢复。这套机制本身是工程界验证过的模式，迁移到 PAICLI 的主要工作不在算法，而在和 PAICLI 现有结构的衔接——失败分类、MCP server 联动、system prompt 信号注入、和并行执行的安全交互。

落地价值要客观评估。PAICLI 当前单 Agent、本地环境为主的场景下，工具持续失败的概率不高，熔断器的收益可能有限。但随着 MCP 工具增多、远程通道引入、Multi-Agent 并行，工具失败的概率和影响都会上升，熔断器的价值会随之放大。建议以"高阈值默认开启、信号注入优先、拦截为辅"的方式灰度落地，先让框架"看见"工具健康度，再逐步让熔断拦截发挥作用，避免过早收紧阈值影响现有体验。这套机制本质上是 PAICLI 走向更复杂工具生态时的基础设施，提前布设比临时补救从容。

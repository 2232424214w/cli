# 02 乐观锁与原子文件写入

## 一、背景：文件写入的并发安全盲区

Agent 框架在文件写入这件事上，有一个很容易被忽视的盲区：并发修改。

PAICLI 的 `write_file` 工具，实现路径是 `PathGuard.resolveSafe` 校验路径 → 读出旧内容用于 diff → `Files.createDirectories` 建父目录 → `Files.writeString` 直接写入。这条路径在单用户、单 Agent 的理想场景下没有问题，但一旦引入并发，就会出现两类风险。

第一类风险是"读改写"的竞态。Agent 在写入前先读了旧内容（用于生成 diff 和触发 LSP 诊断），然后在写入时用新内容覆盖。如果在这两步之间，有另一个进程（可能是另一个 Agent 实例、用户自己在编辑器里改了文件、或者某个 MCP 工具触发了文件变更）也改了这个文件，Agent 的写入就会把对方的修改无声地覆盖掉。Agent 完全不知道自己踩了别人，被覆盖的修改也无处找回。

第二类风险是写入过程的可见性。`Files.writeString` 不是原子的，在写入过程中文件会处于"半成品"状态。如果此时有别的进程读这个文件（比如 LSP 服务器在监听文件变化触发了诊断，或者另一个工具在读），就会读到不完整的内容，可能引发误报或误判。写入中途如果进程崩溃，文件还会停留在损坏状态。

这两类风险在 PAICLI 当前的设计里都没有任何防护。MyCodeAgent 在这件事上做了一套基于乐观锁和原子替换的方案，值得 PAICLI 借鉴。

## 二、PAICLI 现状：直接覆盖，无并发感知

回到 `ToolRegistry.java` 里 `write_file` 的实现看清楚现状。

写入前的"读旧内容"这一步，用的是 `Files.readString(safe)`，读出来的 `before` 字符串只用来生成 diff 和触发后续 observer、LSP 钩子，没有任何地方把它当作"版本基线"去和写入时的实际状态做比对。也就是说，读和写之间没有任何锁定的语义，读出来的内容只是个参考，不参与写入决策。

写入这一步，`Files.writeString(safe, content)` 是直接覆盖目标路径。Java NIO 的 `Files.writeString` 在默认 `CREATE, WRITE, TRUNCATE_EXISTING` 选项下，会先截断文件再写入新内容，整个过程对其他读者可见，不是原子操作。没有临时文件、没有 rename 替换、没有 fsync 保证落盘。

这套实现意味着：PAICLI 假设"在 Agent 运行期间，文件系统只有 Agent 自己在动"。这个假设在单 Agent 单用户时成立，但 PAICLI 的路线图里有 Multi-Agent 并行执行、有 MCP 工具可能操作文件、有微信通道远程触发 Agent，这些场景都会打破这个假设。一旦打破，覆盖丢失和半成品可见就是迟早的事。

另外，PAICLI 的 `revert_turn` 依赖 snapshot 机制（`SideGitManager` / `SnapshotService`），但 snapshot 是按轮次做的，轮次内的中间状态没有保护。如果一轮里先写文件、再写同一个文件，第二次写入覆盖第一次时，第一次的内容并没有被 snapshot 记录，revert 也找不回来。

## 三、MyCodeAgent 的解法：FileSnapshot 与原子替换

MyCodeAgent 的方案核心是一个叫 `FileSnapshot` 的概念，配合 `mkstemp` + `os.replace` 实现原子写入，配合 `os.link` 实现原子创建。它把文件写入变成了一个带版本基线的、对其他读者不可见中间态的过程。

乐观锁的部分是这样的：Agent 在决定要写一个文件之前，先记录这个文件的当前状态作为"基线快照"——在 MyCodeAgent 里这个快照包含文件的 inode、mtime、size 等元信息，或者直接是内容哈希。写入时，框架先检查当前文件系统的实际状态是否还和基线一致：如果一致，说明从读到现在没人动过这个文件，可以安全写入；如果不一致，说明有人抢先改了，Agent 的写入基于的是过期的旧内容，直接覆盖会丢失对方的修改，于是框架拒绝写入，返回一个冲突错误，让 Agent 决定是重新读取再写、还是放弃。

原子写入的部分是这样的：真正写新内容时，不是直接写目标文件，而是先写一个临时文件（用 `mkstemp` 生成唯一临时文件名，避免并发临时文件冲突），把全部内容写进去、fsync 落盘，然后用 `os.replace` 把临时文件原子地重命名成目标文件。`os.replace` 在 POSIX 上是原子的，要么看到旧文件、要么看到新文件，绝不会看到半成品。这样其他读者（LSP、其他工具）要么读到完整的旧内容、要么读到完整的新内容，不会读到写入中途的状态。

原子创建的部分针对"新建文件"场景：用 `os.link` 创建一个硬链接，如果目标已存在则失败，保证"创建"这个动作在并发下也是互斥的，不会两个进程同时创建同一个文件。

这套方案合在一起，把文件写入从"读-改-写"的脆弱模式，变成了"读基线-写临时-原子替换-冲突检测"的健壮模式。代价是多一次临时文件 IO 和一次 rename，但换来的是并发安全和崩溃安全。

## 四、迁移到 PAICLI 的设计建议

把这套思路搬进 PAICLI，要考虑 Java 生态和 PAICLI 现有结构的适配，不能照搬 Python 的 `os.replace` / `os.link`。下面分几层说。

### 4.1 新增的类与职责

建议在 `com.bettercli.tool` 包下新增一个 `FileWriteGuard`，封装乐观锁和原子写入的全部逻辑。它对外暴露两个方法：`beginWrite(path)` 返回一个 `FileBaseline`（包含路径、存在性、size、mtime、内容哈希），`commitWrite(baseline, content)` 执行冲突检测和原子写入，返回写入结果或冲突错误。

`FileBaseline` 是不可变值对象，记录写入前的文件状态。它至少包含：路径的绝对规范化形式、文件是否存在、若存在则记录 size 和 lastModifiedTime、以及内容的 SHA-256 哈希（小文件直接算，大文件可以只取首尾哈希或跳过哈希只靠 mtime+size，权衡性能）。

冲突检测的逻辑放在 `commitWrite` 里：写入前重新读取文件元信息，和 `baseline` 比对。如果文件不存在了（被删）、或 mtime/size 变了、或哈希变了，判定为冲突，拒绝写入并返回 `WriteConflictException`，附带当前实际状态供 Agent 决策。

### 4.2 原子写入的 Java 实现

Java NIO 提供了 `Files.move` 配合 `StandardCopyOptions.ATOMIC_MOVE`，等价于 POSIX 的 `rename`，在支持原子移动的文件系统上是原子的。具体流程是：在目标文件同目录下创建临时文件（用 `Files.createTempFile(dir, prefix, suffix)`，临时文件必须和目标同目录，跨文件系统 rename 不保证原子），写入内容，`Files.move` 时带 `ATOMIC_MOVE` 替换目标。如果文件系统不支持 `ATOMIC_MOVE`（比如某些 Windows 网络挂载），回退到 `Files.move` 的 `REPLACE_EXISTING`，并在文档里标注该路径非原子。

新建文件场景，Java 没有直接的 `os.link` 等价物用于"创建即失败"。可以用 `Files.createFile` 配合 `FileAlreadyExistsException` 判断，但 `createFile` 在存在时抛异常、不存在时创建，本身就是原子的（底层是 `O_CREAT|O_EXCL`），能满足"原子创建"的语义。

### 4.3 与现有 write_file 的衔接

`ToolRegistry.java` 里 `write_file` 的 executor 改造点很集中：把现在的"读旧内容 → `Files.writeString`"两步，换成"`FileWriteGuard.beginWrite` → 生成 diff → `FileWriteGuard.commitWrite`"。diff 生成需要的旧内容，从 `beginWrite` 返回的 baseline 里取（baseline 可以顺带缓存读到的内容，避免二次读）。

冲突发生时，`commitWrite` 抛 `WriteConflictException`，executor 捕获后不要返回"写入失败"这种模糊错误，而是返回结构化的冲突信息：文件被外部修改、当前内容摘要、建议 Agent 重新读取后再写。这样 Agent 在下一轮 ReAct 能拿到明确信号，决定是重新读、合并修改、还是放弃。这个信号配合第一篇的 Completion Gate，效果会叠加——冲突本身就是一种"证据被污染"，Gate 会要求重新验证。

### 4.4 冲突时的合并策略

乐观锁冲突后怎么办，是这套设计里最需要权衡的地方。有三种策略可选。

第一种是"直接拒绝，让 Agent 自己决定"。最简单，但 Agent 可能不知道怎么合并，反复冲突反复失败。第二种是"框架自动尝试三方合并"，用 baseline 版本、Agent 想写的新版本、当前实际版本做三方 diff 合并（类似 git merge），合并成功就写入，合并失败再拒绝。这需要引入一个合并库，PAICLI 可以复用 `snapshot` 模块里已有的 git 能力——`SideGitManager` 本身就基于 git，三方合并是 git 的拿手好戏。第三种是"提示用户介入"，冲突时暂停 Agent，把冲突展示给用户，让用户选保留哪个版本或手动合并。这对应 PAICLI 的 HITL 机制。

建议默认走第一种，但把第二种作为可选增强（复用 git 三方合并），第三种作为高危场景的兜底（通过 HITL）。默认策略保守，避免框架自作主张合并出错误结果；增强策略在用户开启时提供便利；HITL 兜底保证最坏情况下人能介入。

### 4.5 与 snapshot 机制的协同

PAICLI 的 `SnapshotService` 在每轮 ReAct 前做 git 快照，用于 `revert_turn`。引入乐观锁后，要理清两者的职责边界：snapshot 是"轮次级"的回滚点，乐观锁是"单次写入级"的冲突检测。两者不冲突，但要保证 snapshot 不会因为乐观锁的临时文件而污染 git 状态。

具体做法是：`FileWriteGuard` 的临时文件放在 `.bettercli/tmp/` 目录下（或系统临时目录），不放在项目工作区，避免被 `SideGitManager` 的 git add 误纳入。写入成功后临时文件已被 rename 走，自然不会残留。如果写入中途崩溃留下临时文件，启动时清理一次即可。

## 五、迭代步骤

这套设计的落地建议分四步。

第一步，实现 `FileWriteGuard` 的原子写入部分，但不做冲突检测。把 `write_file` 的直接 `Files.writeString` 改成"临时文件 + `ATOMIC_MOVE` 替换"。这一步只解决半成品可见问题，不引入冲突语义，对 Agent 行为零影响，是最安全的切入点。配合单元测试验证：写入中途其他读者读不到半成品、写入后内容完整、临时文件不残留。

第二步，加入 `FileBaseline` 和冲突检测，但默认只检测不拒绝——冲突时记录日志但仍然写入（覆盖）。这一步让框架"看见"冲突，但不改变行为，便于在真实环境观察冲突频率，判断乐观锁到底有没有实际价值。如果观察下来冲突极少，说明 PAICLI 的并发假设目前成立，乐观锁可以缓推；如果冲突频繁，说明确实需要。

第三步，把冲突检测从"只记录"切换到"拒绝并返回结构化错误"，默认开启。这一步真正改变 Agent 行为，需要配合 Agent 提示词的调整——告诉模型遇到 `WriteConflictException` 该怎么处理（重新读、合并或放弃）。

第四步，加入可选的三方合并（复用 git）和 HITL 兜底。这是功能增强，前三步已经把基础打牢。

每一步都要同步更新文档：第一步改 `AGENTS.md` 的工具行为说明，第二到三步在 `docs/` 新建 `phase-25-atomic-write.md`，第四步更新 HITL 和 snapshot 相关文档。

## 六、测试方案

测试分三层。

第一层是 `FileWriteGuard` 的单元测试。覆盖：原子写入后内容完整、临时文件清理、`ATOMIC_MOVE` 不支持时的回退路径、冲突检测的各种触发条件（mtime 变、size 变、哈希变、文件被删、文件从无到有被外部创建）、并发写入同一文件的竞态（多线程同时 commitWrite，只有一个成功，其余冲突）。

第二层是 `write_file` 工具的集成测试。用 mock 文件系统或在临时目录构造场景：Agent 读文件 → 外部修改文件 → Agent 写入，验证返回结构化冲突错误而非静默覆盖；Agent 读文件 → 写入成功 → 验证 LSP 钩子拿到的是完整新内容而非半成品。

第三层是端到端手测。启动两个 Agent 实例操作同一项目，或一个 Agent 加一个手动编辑器修改，观察冲突是否被正确拦截、Agent 是否能根据冲突信号合理恢复。这一层重点验证真实并发下的体感，不追求覆盖全。

测试里有个细节：mtime 在某些文件系统上精度有限（秒级），快速连续修改可能 mtime 不变，所以冲突检测不能只靠 mtime，必须配合 size 和内容哈希。哈希计算对小文件无成本，对大文件要设阈值，超过阈值只算 size+mtime，接受极小概率的漏检，换取写入性能。

## 七、风险与权衡

第一个权衡是性能。乐观锁多一次元信息读取和哈希计算，原子写入多一次临时文件 IO 和 rename。对于 PAICLI 大量的小文件写入（代码文件为主），这部分开销可接受；但如果未来支持大文件写入（比如二进制资源），哈希计算和临时文件空间会成为负担。缓解办法是哈希计算按大小阈值跳过、临时文件写入用流式而非全量缓冲。

第二个权衡是跨平台原子性。`ATOMIC_MOVE` 在 Windows 本地 NTFS 上是原子的，但在某些网络挂载、共享文件夹、WSL 跨文件系统场景下可能不支持，会回退到非原子。PAICLI 是跨平台产品，要明确标注哪些路径不保证原子，并在文档里建议用户把项目放在本地文件系统。这其实是 PAICLI 跨平台适配的一个已知短板，和 `execute_command` 的 `bash -c` 硬编码是同一类问题。

第三个权衡是冲突处理的复杂度。乐观锁一旦真正触发冲突，Agent 的恢复行为就变得复杂——它要重新读、理解外部修改、决定怎么合并。这对模型能力是考验，弱模型可能在冲突后陷入混乱。缓解办法是冲突时优先建议 Agent 重新读取并重新规划，而不是强行合并；同时 HITL 兜底让用户能在模型搞不定时介入。

第四个权衡是和并行工具执行的交互。PAICLI 的 `executeTools` 会并行执行多个工具调用，如果一轮里同时有两个 `write_file` 写同一个文件，乐观锁会让其中一个冲突。这其实是正确行为（并发写同文件本就该拒绝），但要在提示词里告诉模型"不要在同一轮并行写同一个文件"，避免模型困惑。配合第一篇的 `mutating` 标记，变更型工具串行执行能进一步降低这类冲突。

第五个权衡是乐观锁 vs 悲观锁。乐观锁假设冲突罕见，冲突时回退重试；悲观锁假设冲突频繁，写入前先加文件锁。PAICLI 当前场景下冲突确实罕见（单 Agent 为主），乐观锁更合适，开销更低。但如果未来 Multi-Agent 并行写同一项目成为主流，可能要考虑悲观锁。这个选择可以延后决定，先用乐观锁探路。

## 八、小结

乐观锁和原子写入要解决的，是 PAICLI 在文件写入上"假设自己是唯一写者"这个隐性前提。这个前提在当前单 Agent 场景下侥幸成立，但 PAICLI 的演进方向（Multi-Agent、MCP 工具、远程通道）正在一步步打破它。在它被彻底打破之前先把防护立起来，比事后补救成本低得多。

MyCodeAgent 的 `FileSnapshot` 方案给了一个清晰的参照：乐观锁做冲突检测、临时文件加原子替换做崩溃安全、原子创建做互斥。这套思路本身不复杂，迁移到 PAICLI 的主要工作量在 Java NIO 的适配和与现有 `snapshot` 机制的协同，而非重新发明轮子。

落地策略上，建议先做原子写入（零行为改变的纯增强），再做冲突检测的"只记录不拒绝"观察期，最后才真正改变行为。这种"先建防护、再观察、再启用"的节奏，能让 PAICLI 在不破坏现有体验的前提下，逐步获得并发安全能力。和第一篇的 Completion Gate 一样，这套设计的价值不在于立刻解决眼前的问题，而在于在 PAICLI 走向更复杂执行场景之前，把基础设施的短板补齐。
